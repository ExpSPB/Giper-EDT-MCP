# Многопрофильные наборы инструментов MCP

Статус: утверждено пользователем 29 августа 2026 года. Реализация ещё не начата.

## 1. Постановка задачи

Сейчас EDT-MCP использует одну постоянную конфигурацию инструментов для всего рабочего пространства
EDT. Выбор встроенного пресета заменяет эту единственную конфигурацию, но не создаёт отдельный
профиль, к которому можно подключиться независимо.

Требуется подключать к одному экземпляру EDT несколько агентов одновременно, назначать каждому
агенту ролевой профиль MCP и предоставлять только разрешённые этим профилем инструменты.

Основные цели:

- сократить объём `tools/list`, загружаемый в контекст каждого агента;
- разделить ответственность агентов с серверным контролем доступных инструментов;
- сохранить одно рабочее пространство EDT и единый каталог зарегистрированных инструментов;
- изменять профили без перезапуска сервера и отключения остальных агентов;
- сохранить совместимость с существующей однопрофильной конфигурацией клиентов.

Оркестратор назначает агенту endpoint нужного профиля. EDT-MCP не создаёт субагентов, не назначает
им системные промпты и не определяет роль агента автоматически.

## 2. Ограничения протокола и ключевое архитектурное решение

EDT-MCP сейчас ориентирован на MCP 2025-11-25. В этой версии Streamable HTTP может выдавать
`MCP-Session-Id`. В актуальном draft MCP протокольные сессии удаляются, а результат `tools/list` не
должен зависеть от конкретного соединения или изменяться как побочный эффект другого запроса этого
соединения. Набор инструментов может зависеть от авторизации или входных данных HTTP-запроса и может
изменяться глобально с отправкой уведомления об изменении списка.

Источники:

- [MCP 2025-11-25: Streamable HTTP и управление сессиями](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)
- [Актуальный draft: удаление протокольных сессий](https://modelcontextprotocol.io/specification/draft/changelog)
- [Актуальный draft: контракт инструментов](https://modelcontextprotocol.io/specification/draft/server/tools)

Поэтому профиль выбирается URL подключения к MCP и остаётся постоянным для этого логического
сервера. Профиль не выбирается изменяемым состоянием соединения или сессии. Явный endpoint профиля
предоставляет фиксированную allowlist инструментов. Такая модель работает и с текущими сессионными
клиентами, и с будущими stateless-клиентами.

Если корректный идентификатор в URL не существует или соответствующий профиль отключён, endpoint
разрешается в профиль `default`. Это fallback маршрутизации, а не переключение профиля состоянием
сессии. Факт подмены обязательно отражается в диагностике и журнале.

Существующий механизм progressive disclosure не расширяется до состояния отдельного профиля или
сессии агента. Пока сервер поддерживает протокол 2025-11-25, он остаётся механизмом совместимости
старого endpoint `/mcp`. Явные endpoint'ы профилей всегда имеют фиксированный набор инструментов.

## 3. Результаты исследования текущей реализации

Добавить несколько записей пресетов недостаточно для изоляции одновременно работающих клиентов.
Если не указано иное, пути ниже приведены относительно
`mcp/bundles/fm.giper.edt.mcp.server/src/fm/giper/edt/mcp/server/`.

- `ToolPreset` — enum, каждое значение которого содержит только предопределённый набор отключённых
  инструментов (`preferences/ToolPreset.java:14-35`). Применение пресета перезаписывает единственный
  сохранённый набор (`preferences/ToolSettingsService.java:409-416`).
- Singleton `ToolSettingsService` читает и записывает глобальное значение `PREF_DISABLED_TOOLS`
  (`preferences/ToolSettingsService.java:116-126`, `136-151`, `311-320`).
- Методы `McpToolRegistry.getEnabledTools()`, `getVisibleTools()` и `isToolEnabled()` используют этот
  глобальный сервис (`tools/McpToolRegistry.java:139-190`). Поэтому и публикация инструментов, и
  разрешение прямого вызова используют одну политику на весь workbench.
- `ToolsetState` является singleton. Раскрытие progressive toolset одним клиентом раскрывает его для
  всех клиентов (`tools/ToolsetState.java:24-34`, `48-104`).
- `McpProtocolHandler` хранит capabilities последнего инициализированного клиента в одном atomic
  reference и явно предполагает работу только одного клиента
  (`protocol/McpProtocolHandler.java:85-96`).
- Плагин выдаёт случайный `Mcp-Session-Id`, но не сохраняет и не проверяет его. `DELETE` принимается
  без освобождения состояния сессии (`transport/McpHttpHandler.java:138-142`, `342-358`).
- `SseStreamRegistry` рассылает сообщение во все открытые SSE-потоки
  (`SseStreamRegistry.java:35-36`, `89-123`), хотя MCP 2025-11-25 требует отправлять серверное
  сообщение только в один из одновременно открытых потоков клиента.
- После изменения набора инструментов страница настроек перезапускает весь MCP-сервер
  (`preferences/McpServerPreferencePage.java:101-127`). При нескольких агентах это без необходимости
  разорвёт все их подключения.
- Proxy использует одну backend-сессию и один кеш списка инструментов на экземпляр EDT. Все запросы
  направляются на `/mcp` backend'а
  (`proxy/src/main/java/fm/giper/edt/mcp/proxy/Backend.java:58-81`), поэтому выбранный клиентом профиль
  будет потерян.

Зарегистрированные объекты `IMcpTool` и сервисы EDT могут остаться общими. Недостающая граница —
контекст запроса с профилем, однозначно выбранным endpoint'ом.

## 4. Термины

| Термин | Значение |
|---|---|
| Каталог инструментов | Все зарегистрированные в workbench экземпляры `IMcpTool`. Каталог общий и не зависит от профиля. |
| Пресет | Встроенный шаблон: All Tools, Analysis Only, Code Review или Development. Применение пресета заменяет выбор в редакторе текущего профиля, но не создаёт endpoint. |
| Профиль | Именованная постоянная allowlist со стабильным идентификатором endpoint. |
| Endpoint профиля | URL отдельного логического MCP-сервера, набор инструментов которого определяется профилем. |
| Транспортная сессия | Механизм совместимости с 2025-11-25 для capabilities клиента и маршрутизации SSE. Никогда не является источником выбора профиля. |
| Разрешённый инструмент | Зарегистрированный инструмент из allowlist профиля. Он публикуется и может вызываться через endpoint профиля. |

В интерфейсе описание профиля может называться ролью, но отдельной сущности «роль» в runtime нет.
Проверяемой сервером единицей является профиль.

## 5. Границы доработки

### Входит в объём

- постоянное хранение и CRUD нескольких профилей;
- выбор профиля стандартным URL MCP;
- учёт профиля в `tools/list`, `resources/list`, `resources/read` и `tools/call`;
- самодиагностика активного профиля и обнаружение доступных профилей через `get_server_status`;
- контекст запроса с учётом версии протокола и корректная работа с сессиями 2025-11-25;
- адресные уведомления об изменении списка инструментов профиля;
- миграция текущей конфигурации инструментов в профиль по умолчанию;
- поддержка прямого подключения к плагину и подключения через EDT-MCP proxy;
- указание профиля в логах и истории MCP;
- модульные, интеграционные, live e2e и conformance-проверки.

### Не входит в объём

- создание субагентов и управление ими;
- передача агенту системного промпта или инструкции его роли;
- использование идентификатора профиля как секрета или учётных данных;
- отдельные токены авторизации, правила PII, разрешения опасных операций и значения параметров для
  каждого профиля;
- progressive disclosure на уровне профиля или сессии;
- изоляция проектов и Git worktree;
- сериализация или разрешение конфликтующих изменений нескольких агентов;
- изменение реализаций инструментов и их правил транзакций EDT;
- полная реализация будущей версии MCP в рамках этой доработки;
- выгрузка и загрузка всех профилей в файл (JSON/XML) для обмена между воркспейсами —
  отдельная следующая доработка, см. `multi-profile-implementation-plan.md` §20.

Профиль является границей возможностей внутри авторизованного сервера, но не границей безопасности
между взаимно недоверенными пользователями. Клиент, имеющий доступ к серверу и знающий URL другого
профиля, сможет подключиться к нему.

## 6. Функциональные требования

### 6.1 Управление профилями

1. Пользователь может создавать, копировать, переименовывать, отключать, редактировать и удалять
   профили в настройках MCP Server.
2. У профиля есть неизменяемый URL-safe идентификатор, изменяемое отображаемое имя и описание.
3. Идентификатор соответствует `[a-z0-9][a-z0-9_-]{0,63}`. Значение `default` зарезервировано.
4. Профиль по умолчанию нельзя удалить или отключить.
   Он также используется как fallback для неизвестных и отключённых профилей, поэтому его набор
   следует делать консервативным и достаточным для безопасной диагностики.
5. Новый профиль создаётся на основе выбранного встроенного пресета. Последующие ручные изменения
   профиля не изменяют пресет и не создают новый пресет.
6. Профиль хранит явную allowlist. Инструмент, добавленный в новой версии плагина, запрещён во всех
   существующих профилях, пока пользователь явно не включит его или повторно не применит пресет.
   Это fail-closed поведение сохраняет стабильность ролевых наборов после обновления.
7. Имена удалённых или неизвестных инструментов сохраняются для диагностики, но не влияют на
   runtime. Интерфейс отмечает их как недоступные и не подставляет вместо них другие инструменты.
8. Сохранение профилей публикует единый неизменяемый snapshot конфигурации. Параллельный запрос видит
   либо полное старое, либо полное новое состояние, но не частично сохранённый профиль.
9. Редактирование профиля не перезапускает MCP-сервер. Удаление инструмента влияет уже на следующий
   вызов. Подключённые к профилю клиенты получают уведомление средствами согласованной версии
   протокола.

### 6.2 Endpoint'ы и выбор профиля

Сервер предоставляет:

- `http://127.0.0.1:<port>/mcp` — совместимый endpoint профиля `default`;
- `http://127.0.0.1:<port>/mcp/profiles/<profileId>` — явный endpoint с фиксированным профилем.

Каждый явный путь считается отдельным логическим MCP-сервером, использующим общий процесс и каталог
инструментов. Для диагностики его `serverInfo.name` содержит идентификатор профиля, но имена
инструментов не изменяются.

Профиль выбирается URL, потому что все MCP-клиенты позволяют настроить URL сервера, а произвольные
HTTP-заголовки поддерживаются не везде. Профиль присутствует в каждом запросе и в sessionful, и в
stateless-транспорте.

Чтобы действительно сократить контекст, оркестратор должен предоставить агенту только назначенный
endpoint. Если одному агенту передать несколько endpoint'ов профилей, клиент может загрузить их
совокупное описание инструментов.

Если `<profileId>` синтаксически корректен, но профиль неизвестен или отключён, сервер успешно
обслуживает запрос с эффективным профилем `default`. Это позволяет агенту продолжить работу при
устаревшей или ошибочной конфигурации MCP-host.

Fallback не должен быть молчаливым:

- `serverInfo.name` идентифицирует эффективный профиль `default`;
- результат `initialize` добавляет в стандартное поле `instructions` предупреждение о fallback и
  рекомендацию вызвать `get_server_status`;
- `get_server_status` сообщает исходно запрошенный идентификатор, эффективный профиль и причину
  fallback;
- сервер записывает предупреждение в журнал без токенов, аргументов инструментов и иных секретов;
- `tools/list`, ресурсы и прямые вызовы немедленно проверяются по allowlist `default`.

Синтаксически некорректный идентификатор, некорректное percent-encoding, лишний сегмент пути или
попытка path traversal отклоняются с HTTP 400 и не приводят к fallback. Это ошибка маршрута, а не
отсутствующий профиль.

### 6.3 Самодиагностика и обнаружение профилей

`get_server_status` является обязательным read-only meta-инструментом каждого профиля и не может
быть отключён. Это небольшое исключение из пользовательской allowlist необходимо, чтобы агент всегда
мог подтвердить фактическую конфигурацию подключения.

Обычный вызов `get_server_status` дополнительно возвращает объект `activeProfile`:

```text
activeProfile
  requestedProfileId идентификатор, запрошенный в URL; `default` для `/mcp`
  id                 идентификатор фактически применённого профиля
  displayName        отображаемое имя
  description        описание назначенной роли
  revision           текущая ревизия
  endpoint           канонический URL фактически применённого профиля
  allowedToolCount   количество разрешённых инструментов
  fallbackApplied    признак подмены на `default`
  fallbackReason     `UNKNOWN_PROFILE` или `DISABLED_PROFILE`; отсутствует без fallback
  warning            краткое объяснение фактически применённого набора; отсутствует без fallback
```

Вызов `get_server_status(includeProfiles=true)` дополнительно возвращает компактный массив
`availableProfiles`, отсортированный по `id`. Для каждого включённого профиля выдаются `id`,
`displayName`, `description`, `endpoint`, `revision` и `allowedToolCount`. Полные allowlist в этот
ответ не включаются, чтобы не расходовать контекст повторной передачей каталога инструментов.

Если описания недостаточно для выбора, агент может явно вызвать
`get_server_status(includeProfiles=true, includeProfileTools=true)`. Тогда каждый элемент
`availableProfiles` дополнительно содержит отсортированный массив `allowedTools`. Большой список
передаётся только по запросу и не увеличивает постоянный payload `tools/list`. Параметр
`includeProfileTools` без `includeProfiles=true` отклоняется как некорректная комбинация.

`allowedToolCount` и опциональный `allowedTools` описывают эффективную поверхность endpoint, включая
обязательный `get_server_status`, а не только сохранённую пользовательскую allowlist.

Отключённые профили в `availableProfiles` не публикуются. `initialize` по неизвестному или
отключённому endpoint завершается успешно с профилем `default`. После подключения
`activeProfile.id` является авторитетным подтверждением фактически применённого профиля, а
`requestedProfileId`, `fallbackApplied` и `fallbackReason` позволяют обнаружить ошибку настройки.

Агент может по описаниям выбрать или предложить подходящий профиль, но не может переключить профиль
текущего MCP-подключения. Для переключения MCP-host или оркестратор создаёт новое подключение к URL из
`availableProfiles`. Сам агент должен считать `activeProfile.id`, а не `requestedProfileId`,
источником истины о доступном наборе и явно сообщать оркестратору о fallback.

Если в будущем появится per-profile авторизация, `availableProfiles` фильтруется по правам текущего
запроса. Идентификатор профиля по-прежнему не считается учётными данными.

### 6.4 Поведение транспорта с учётом версии протокола

Запрошенный профиль всегда определяется нормализованным путём запроса, после чего resolver получает
эффективный профиль или применяет описанный fallback на `default`. Идентификатор сессии, заголовок,
тело запроса или аргумент инструмента не могут выбрать или изменить этот результат.

Для протокола 2025-11-25:

1. `initialize` может создать отслеживаемую транспортную сессию, привязанную к пути endpoint, и
   вернуть её `MCP-Session-Id`.
2. Сессия хранит согласованные capabilities клиента, запрошенный путь и выбранный для серверных
   сообщений поток. Эффективный профиль повторно разрешается по актуальному snapshot на каждый
   запрос; сессия не хранит альтернативный набор инструментов.
3. Последующие запросы с идентификатором сессии должны использовать тот же путь профиля.
4. Отсутствующий обязательный заголовок сессии приводит к HTTP 400, неизвестная или завершённая
   сессия — к HTTP 404, а `DELETE` завершает сессию.
5. Количество сессий ограничено, неактивные сессии удаляются по тайм-ауту, поэтому брошенные клиенты
   не могут бесконечно увеличивать потребление памяти.

Старый `/mcp` в течение определённого периода совместимости продолжает принимать клиентов без
поддержки сессий. Такие запросы используют профиль `default` и отсутствующие capabilities клиента.

В будущей stateless-версии протокола профиль по-прежнему определяется путём каждого запроса.
`MCP-Session-Id` не выдаётся и не требуется, а метаданные протокола и capabilities читаются из
запроса по правилам этой версии. Если ранее отсутствовавший профиль создан или отключённый профиль
включён, следующий запрос к его пути использует уже этот профиль; изменение поверхности публикуется
как обычное глобальное изменение данного логического endpoint. Репозиторий профилей и политика
инструментов не меняются.

### 6.5 Эффективная политика инструментов

Для контекста запроса `C`:

```text
resolution(C) = resolve(path(C), profilesSnapshot)
allowed(C) = зарегистрированные инструменты ∩ resolution(C).effectiveProfile.allowedTools
```

- `tools/list` и `resources/list` используют `allowed(C)` с детерминированной сортировкой по имени.
- `resources/read` разрешён только для руководства инструмента из `allowed(C)`.
- `tools/call` требует наличия инструмента в `allowed(C)`, даже если клиент сформировал прямой вызов
  известного инструмента вручную.
- Ошибка запрещённого вызова называет активный профиль и объясняет, где включить инструмент. Она не
  должна утверждать, что инструмент не существует.
- Два клиента с одной ревизией профиля получают одинаковый список независимо от соединения и
  предыдущих запросов.
- `get_server_status` всегда добавляется к эффективной поверхности как обязательный безопасный
  meta-инструмент, даже если его имя отсутствует в сохранённой allowlist.

Явные endpoint'ы профилей не публикуют `enable_toolset`. Прямой вызов этого инструмента отклоняется
как неподдерживаемый для endpoint с фиксированным профилем. `list_toolsets` может оставаться доступным
как справочник по каталогу, если он включён в профиль.

Старый endpoint `/mcp` может сохранить существующее progressive-disclosure поведение для
совместимости с 2025-11-25. Это состояние не влияет на явные endpoint'ы профилей и не является частью
контракта многопрофильности. Его последующая отмена должна выполняться вместе с переходом на новую
версию протокола, а не скрыто в рамках этой доработки.

Глобальная политика подтверждения опасных действий применяется дополнительным шлюзом после проверки
профиля. Глобальные значения параметров инструментов, авторизация, remote binding, PII/redaction и
plain-text mode также остаются общими для всех профилей.

### 6.6 Одновременная работа

Два клиента с разными профилями могут одновременно инициализироваться, получать список инструментов,
читать ресурсы и вызывать разрешённые инструменты. Выбор профиля, capabilities и уведомления не
должны переходить между клиентами. Два клиента одного профиля должны видеть одну ревизию профиля.

Профили не делают безопасной параллельную запись в один проект EDT. Согласованность изменений
по-прежнему определяется транзакциями инструментов, хешами содержимого, EDT jobs и блокировками EDT.
Рекомендуемая организационная модель — не более одной изменяющей роли на проект одновременно, а
профили аналитика и ревьюера должны быть read-only. Планировщик ресурсов или аренда проекта требуют
отдельной спецификации.

## 7. Модель данных и хранение профилей

Логическая модель:

```text
ToolProfile
  id                 стабильный идентификатор endpoint
  displayName        изменяемое имя в интерфейсе
  description        необязательное описание роли
  enabled            разрешены ли запросы к профилю
  allowedTools       явный набор имён инструментов
  revision           монотонно возрастающая ревизия конфигурации
```

Профили хранятся за интерфейсом `ToolProfileRepository`. Протокол, UI и proxy зависят от контракта
репозитория, а не от ключей Eclipse Preferences. Первая реализация использует версионированный JSON
в instance preferences плагина и заменяет документ одним значением. Документ содержит версию схемы и
имеет детерминированный порядок элементов.

Репозиторий публикует неизменяемый `ToolProfileSnapshot` через одну volatile/atomic ссылку, повторяя
принцип целиком заменяемого snapshot из `McpToolRegistry.replaceAll()`.

Значения `ToolPreset` остаются встроенными шаблонами. Совпадение с пресетом в редакторе определяется
сравнением allowlist выбранного профиля с текущим каталогом. Значение Custom вычисляется интерфейсом и
не сохраняется как отдельный тип профиля.

## 8. Целевая архитектура

```text
MCP-клиент агента
      |
      | /mcp/profiles/reviewer
      v
McpHttpHandler -> endpoint resolver -> McpRequestContext(requestedId, effectiveProfile, protocol)
                                                |
                                                v
                                     ToolProfileRepository
                                                |
                              +-----------------+-----------------+
                              v                                   v
                   profile-aware tools/list            profile-aware tools/call
                              |                                   |
                              +---------- McpToolRegistry --------+
                                           общий каталог
```

### 8.1 Контекст запроса

`McpRequestContext` — неизменяемое значение, явно передаваемое из транспорта в протокольный
диспетчер. Оно содержит запрошенный идентификатор, эффективный профиль, признак и причину fallback,
ревизию профиля, согласованную версию протокола и соответствующие capabilities или ссылку на
транспортную сессию.

Отдельный результат `ProfileResolution` формируется по одному snapshot репозитория и используется до
конца запроса. За счёт этого один запрос не может начать выполняться с исходным профилем, а завершить
проверку прав по `default`. Следующий запрос получает новый snapshot и видит создание, отключение или
удаление профиля.

Контекст нельзя хранить в `ThreadLocal`: прерываемые вызовы переходят между executor-потоками, а
in-process bridge не имеет HTTP-идентичности потока.

`McpProtocolHandler.processRequest` принимает контекст и передаёт его в dispatch, формирование списков,
чтение ресурсов и вызов инструмента. Сам handler больше не хранит глобальный reference capabilities
последнего клиента.

Чтобы не изменять каждую существующую реализацию инструмента, в `IMcpTool` можно добавить
context-aware точку входа с default-реализацией, вызывающей существующий метод только с параметрами.
Переопределять её должны лишь инструменты, которым нужен профиль для поведения или диагностики.

### 8.2 Разделение каталога и политики

`McpToolRegistry` отвечает только за регистрацию и поиск. Он больше не должен неявно обращаться к
`ToolSettingsService`. Отдельный profile-aware resolver вычисляет разрешённое представление каталога
по контексту запроса.

Это позволяет обслуживать несколько профилей одним неизменяемым каталогом без копирования объектов
инструментов и тестировать политику без Eclipse Preference Store.

### 8.3 Серверные сообщения и изменение профиля

После изменения сохранённого профиля сервер уведомляет каждого подходящего клиента этого логического
endpoint ровно один раз, используя механизм уведомлений или подписок согласованной версии протокола.
Сообщение не отправляется клиентам других профилей и не дублируется в нескольких потоках одного
клиента.

При отключении или удалении профиля его endpoint переходит на поверхность `default`; подключённые к
этому пути клиенты получают уведомление об изменении списка и предупреждение о fallback. При
последующем создании или включении профиля тот же путь переходит на его поверхность с таким же
уведомлением. Это изменение является общей реконфигурацией логического endpoint, а не per-session
переключением.

Удалённый из профиля инструмент становится недоступен до отправки уведомления. Ошибка доставки
уведомления не может оставить старое разрешение действующим.

### 8.4 In-process bridge

Существующие методы `IEdtMcpBridge.listTools()` и `callTool(...)` сохраняют поведение профиля
`default`. Profile-aware overload'ы могут быть добавлены без нарушения совместимости с существующими
потребителями Workmate. Bridge использует явный синтетический контекст и не обходит проверку профиля.

### 8.5 Наблюдаемость

История MCP сохраняет `requestedProfileId`, эффективный `profileId` и причину fallback, а для
сессионных версий протокола — также идентификатор сессии. Логи и status bar содержат профиль,
например `MCP[reviewer]: read_module_source` или `MCP[missing -> default]: get_server_status`. Имя
агента не выводится из профиля. Секреты и токены авторизации не сохраняются в профилях или истории.

## 9. Интерфейс настроек

Вкладка Tools становится редактором профилей:

- селектор профиля и действия Add, Duplicate, Rename, Disable и Delete;
- read-only предпросмотр endpoint и действие Copy URL;
- поля отображаемого имени и описания; описание используется агентами при выборе профиля, поэтому UI
  объясняет его назначение и рекомендует заполнять его как краткое описание роли;
- существующие селектор пресета, дерево групп, отдельные checkbox инструментов, счётчик и описание
  редактируют выбранный профиль;
- значения параметров и разрешения опасных действий явно помечены как глобальные;
- dirty-state отслеживается по профилям и сохраняется одним snapshot;
- профиль `default` визуально отмечен, не может быть удалён или отключён; UI предупреждает, что он
  используется как fallback неизвестных и отключённых endpoint'ов, и рекомендует консервативный
  набор инструментов.

Глобальная настройка Progressive disclosure помечается как относящаяся только к старому endpoint
`/mcp` и не становится полем профиля.

Restore Defaults сбрасывает только выбранный профиль и требует подтверждения. Это действие не должно
удалять остальные профили. Отдельный явный сброс всех профилей при необходимости может быть добавлен
позже.

## 10. Обратная совместимость и миграция

При первом запуске новой версии, если документа профилей ещё нет:

1. Регистрируется текущий каталог инструментов.
2. Текущее значение `PREF_DISABLED_TOOLS` читается и проходит существующие миграции.
3. Создаётся профиль `default`, allowlist которого равна текущему каталогу за вычетом отключённых
   инструментов. Так сохраняется точная поверхность до обновления.
4. Существующая настройка progressive disclosure остаётся привязанной к старому поведению `/mcp` и
   не копируется в профиль.
5. Новая схема сохраняется только после полной проверки созданного профиля.

Как минимум в течение одного совместимого релиза сохранение профиля `default` зеркально обновляет
дополнение в `PREF_DISABLED_TOOLS`. Это позволяет после downgrade получить приблизительно тот же
набор инструментов. Дополнительные профили старой версией игнорируются.

Существующим клиентам `/mcp` не требуется менять конфигурацию. Имена и смысл пресетов сохраняются, но
применение пресета влияет только на выбранный в интерфейсе профиль.

## 11. Требования к proxy

Изоляция профилей должна работать через `edt-mcp-proxy`. Иначе proxy незаметно переключит соединение
на профиль backend'а по умолчанию.

- Proxy принимает пути `/mcp` и `/mcp/profiles/<profileId>`.
- Нормализованный запрошенный `profileId` передаётся backend без подмены значением из тела или
  заголовка. Решение о fallback принимает backend как источник истины; proxy не реализует
  независимую таблицу профилей.
- Для сессионных версий протокола клиентская сессия привязывается к пути профиля, а backend-сессии
  индексируются по `(backend, requestedProfileId)`.
- Для stateless-версий proxy не вводит собственную протокольную сессию, но направляет запрос на
  соответствующий URL профиля backend'а.
- Кеш `tools/list` индексируется по запрошенному идентификатору, эффективному идентификатору и
  ревизии профиля. Ответ fallback-подключения не используется как диагностический ответ явно
  настроенного `default`, даже если поверхности инструментов совпадают.
- Маршрутизируемые и fan-out вызовы, retry после перезапуска backend'а и повторный initialize
  сохраняют профиль.
- Обнаружение проектов может использовать внутреннее подключение к профилю backend'а по умолчанию.
  Это внутренняя функция роутера, которая не расширяет публикуемую или вызываемую поверхность
  клиентского профиля.
- `router_status` и `router_refresh` остаются обязательными proxy-core инструментами и являются
  единственным документированным дополнением к поверхности профиля backend'а.

## 12. Обработка ошибок

| Ситуация | Требуемый результат |
|---|---|
| Синтаксически корректный неизвестный профиль | Запрос успешно выполняется через `default`; status и журнал содержат `UNKNOWN_PROFILE`. |
| Синтаксически корректный отключённый профиль | Запрос успешно выполняется через `default`; status и журнал содержат `DISABLED_PROFILE`. |
| Некорректный идентификатор или путь профиля | HTTP 400 без fallback. |
| Нет обязательной сессии 2025-11-25 | HTTP 400 с требованием выполнить initialize. |
| Неизвестная или завершённая сессия 2025-11-25 | HTTP 404 с требованием повторить initialize. |
| Сессия отправлена на путь другого профиля | HTTP 404 без раскрытия существования другого профиля. |
| Инструмент зарегистрирован, но запрещён профилем | Успешный envelope `tools/call` с `isError: true`, именем профиля и местом настройки. |
| Прямой `enable_toolset` на явном профиле | Ошибка запрещённого или неподдерживаемого инструмента; профиль не изменяется. |
| Профиль удалён или отключён после успешного подключения | Текущий атомарный запрос завершается по исходному snapshot; последующие запросы используют `default`, получают status-warning и обновлённый `tools/list`. |
| Сохранённый документ профилей повреждён | Fail-closed профиль `default` с безопасными заводскими значениями; ошибка записывается в лог, повреждённое значение сохраняется для диагностики. |
| После обновления зарегистрирован новый инструмент | Инструмент запрещён во всех существующих профилях до явного включения. |

## 13. Требования к проверкам

### Модульные и компонентные тесты

- проверка идентификаторов и путей, CRUD, детерминированного хранения и атомарной публикации snapshot;
- однократная миграция точно сохраняет текущую поверхность инструментов;
- новые инструменты запрещены существующими allowlist;
- применение пресета изменяет только выбранный профиль;
- детерминированное пересечение разрешений для списков, ресурсов и вызовов;
- прямой вызов не обходит запрет профиля;
- `get_server_status` всегда доступен, подтверждает активный профиль и не сообщает другой профиль как
  текущий;
- неизвестный и отключённый идентификаторы дают прозрачный fallback: успешный `initialize`,
  предупреждение в `instructions`, эффективный `default`, правильные `requestedProfileId`,
  `fallbackReason` и status-warning;
- некорректный путь не маскируется fallback и отклоняется до протокольного dispatch;
- `get_server_status(includeProfiles=true)` возвращает только включённые профили, стабильные endpoint'ы
  и компактные метаданные без полных allowlist;
- `includeProfileTools=true` по явному запросу возвращает детерминированные эффективные списки
  инструментов и не меняет активный профиль;
- два клиента одной ревизии профиля получают одинаковый список независимо от прошлых запросов;
- capabilities изолированы для сессионных версий протокола;
- уведомления отправляются клиентам затронутого логического endpoint и не дублируются по потокам;
- изменение профиля не перезапускает сервер;
- совместимое поведение старого `/mcp`;
- явный профиль не может изменить свою поверхность через `enable_toolset`;
- поведение bridge с профилем `default` и явным профилем;
- изоляция пути, сессий, backend-сессий, кеша, retry и fan-out в proxy.

### Live e2e сценарий

Два MCP-клиента подключаются к одному экземпляру EDT:

1. Клиент A подключается к профилю анализа или ревью, клиент B — к профилю разработки.
2. Оба клиента вызывают `get_server_status` и получают собственный правильный `activeProfile`.
3. Клиент A запрашивает `includeProfiles=true`, видит оба включённых профиля и их разные endpoint'ы,
   но его активный профиль и набор инструментов не изменяются.
4. Результаты `tools/list` клиентов отличаются согласно настройкам и остаются стабильными после
   посторонних запросов.
5. Оба клиента параллельно вызывают разрешённый инструмент чтения и получают независимые корректные
   ответы.
6. Клиент A вручную вызывает инструмент разработки и получает ошибку запрета профиля.
7. Клиент B вызывает тот же инструмент и доходит до обычного пути выполнения.
8. Клиент вызывает `enable_toolset` через явный профиль; списки инструментов обоих клиентов не
   изменяются.
9. Во время работы клиентов инструмент удаляется из профиля B. Следующий вызов B запрещён без
   перезапуска сервера, а A остаётся подключённым.
10. Проверки discovery, поверхности, стабильности и невозможности обхода запрета повторяются через
    proxy.
11. Клиент C подключается сначала к неизвестному, затем к отключённому профилю. Оба `initialize`
    успешны, `tools/list` точно совпадает с эффективной поверхностью `default`, а
    `get_server_status` различает `UNKNOWN_PROFILE` и `DISABLED_PROFILE` и не выдаёт запрошенный
    профиль за активный.
12. Отключение активного профиля во время работы переводит его endpoint на `default` без частично
    применённого запроса; последующий вызов ранее разрешённого только этим профилем инструмента
    запрещается, а клиент получает уведомление об изменении списка.

Текущий conformance suite MCP 2025-11-25 должен сохранить или улучшить baseline. Архитектура также
должна пройти целевые проверки правил актуального stateless draft: профиль выбирается путём запроса,
а список инструментов фиксированного профиля не зависит от соединения и не изменяется как побочный
эффект запроса.

## 14. Критерии приёмки

Спецификация выполнена, когда:

- не менее двух включённых профилей одновременно работают через разные URL одного EDT-сервера;
- endpoint каждого профиля возвращает детерминированную фиксированную поверхность своей ревизии;
- `get_server_status` позволяет подтвердить активный профиль, а `includeProfiles=true` — получить
  компактный список доступных профилей и URL для нового подключения;
- неизвестный или отключённый профиль прозрачно использует `default`, причём агент видит запрошенный
  и эффективный идентификаторы, причину fallback и предупреждение;
- синтаксически некорректный путь не приводит к fallback;
- обнаружение профилей не переключает текущее подключение и не расширяет его права;
- `tools/call` проверяет профиль endpoint даже для вручную сформированного прямого вызова;
- выбор профиля не зависит от изменяемого состояния сессии или соединения;
- capabilities сессионных клиентов и маршрутизация серверных сообщений корректно изолированы;
- изменение профиля применяется без перезапуска и отключения посторонних клиентов;
- старый `/mcp` сохраняет текущую конфигурацию `default` и progressive-disclosure поведение;
- существующая установка мигрирует без добавления или потери ранее настроенных инструментов;
- новые инструменты не появляются в существующих профилях автоматически;
- прямое подключение и proxy ведут себя одинаково;
- глобальные шлюзы безопасности продолжают работать после проверки профиля;
- все требуемые unit, e2e, proxy и conformance-проверки проходят.

Эти профили являются примерами, а не обязательными встроенными значениями.

| Профиль | Типичный набор |
|---|---|
| `analyst` | Обнаружение проектов, диагностика, чтение метаданных и кода, ссылки, проверка запросов; без записи и запусков. |
| `implementer` | Инструменты аналитика, ограниченная запись BSL и метаданных, рефакторинг; raw Git только при явном включении. |
| `tester` | Диагностика проекта, приложения, обновление базы, YAXUnit, debug и test jobs; запись исходников опциональна. |
| `reviewer` | Пресет Code Review; все изменяющие инструменты запрещены. |

Наборы оставлены примерами, потому что процессы в репозиториях различаются. Поставка дополнительных
встроенных ролей создаст обязательство обновлять каждую роль при появлении каждого нового инструмента.
Для повторного использования уже существуют пресеты.

## 16. Утверждённые решения

1. Профиль выбирается путём `/mcp/profiles/<id>`, а `/mcp` является alias профиля `default`.
2. Каждый явный endpoint профиля является логическим MCP-сервером с фиксированной поверхностью;
   профиль никогда не определяется состоянием сессии.
3. Профили используют явные allowlist и fail-closed обработку инструментов будущих версий.
4. Существующий progressive-disclosure механизм остаётся поведением старого `/mcp` и не расширяется
   на профили.
5. Изменения профилей публикуются атомарно без перезапуска MCP-сервера.
6. Поддержка proxy входит в ту же доработку, а не откладывается как последующее исправление
   совместимости.
7. Профили разделяют контекст и возможности, но не являются security principals или блокировками
   параллельного доступа.
8. Активный профиль и доступные профили диагностируются через обязательный `get_server_status`, без
   добавления отдельного `list_profiles` в контекст каждого агента.
9. Неизвестный или отключённый профиль использует `default`; подмена всегда отражается в status,
   журнале и proxy, а некорректный путь отклоняется без fallback.
